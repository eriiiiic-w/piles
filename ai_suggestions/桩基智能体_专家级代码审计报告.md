# 桩基智能体代码审计与专家级重构建议

## 审计范围

本次审计基于以下 5 个核心文件：

- `server/core/prediction.py`
- `server/services/predict_service.py`
- `server/database.py`
- `server/api/project.py`
- `client/src/components/three/PileLayer.tsx`

该项目当前已经具备：

- 较清晰的前后端分层
- 可运行的多项目架构
- 工程化的 3D 渲染能力
- 实际工程场景导向的数据结构设计

但从“可运行工程”到“工业级软件”之间，还存在若干关键架构风险。

以下建议按：

- 严重程度
- 长期影响
- 可扩展性
- 性能风险
- 工程稳定性

进行排序。

# 一、总体评价（非常关键）

这个项目已经不是“学生项目”。

# 三、prediction.py 的关键问题

---

## 问题 1：重复构建 Kriging 对象（严重性能问题）

当前：

```python
ok = OrdinaryKriging(...)
```

在每一次预测、每一层循环中都会重新创建。

这是当前整个系统最大的 CPU 性能黑洞。

---

## 为什么危险

PyKrige 的初始化非常昂贵：

- variogram fitting
- covariance matrix
- inversion

都会重复计算。

你现在：

760 根桩 × 15 土层

意味着：

# 超过一万次 Kriging 初始化

这是灾难性的。

---

## 专业级改法

### 必须改为：

# “每层缓存 Kriging Model”

例如：

```python
kriging_models[layer] = OrdinaryKriging(...)
```

之后：

```python
model.execute(...)
```

直接复用。

---

## 预期收益

实际工程中：

性能可能提升：

# 20~100 倍

这是目前 ROI 最高的优化。

---

# 问题 2：DataFrame 过滤重复执行

当前：

```python
layer_data = geo_df[geo_df['土层名称'] == layer]
```

在循环中反复执行。

Pandas filtering 很贵。

---

## 应改为预分组

在函数外：

```python
layer_groups = {
    layer: df
    for layer, df in geo_df.groupby('土层名称')
}
```

然后直接读取。

你在工作日志里已经提到：

“预分组优化”。

这是正确方向。

但建议：

# 下沉到 core 层

不要放 service 层。

因为这是：

算法输入优化。

属于 core 职责。

---

# 问题 3：异常处理吞掉真实错误

当前：

```python
except Exception:
    return float(np.mean(val))
```

这属于：

# 静默失败

危险级别很高。

---

## 为什么危险

可能出现：

- variogram 崩溃
- NaN
- 奇异矩阵
- 数据异常

但系统表面正常。

工程软件最怕：

# “错误但看起来正常”

---

## 建议

至少：

```python
except Exception as e:
    logger.exception(...)
```

必须记录：

- layer
- pile_no
- coordinates
- variogram model

否则后期无法定位预测错误。

# 五、database.py（最危险模块之一）

---

# 问题 1：全局 engine 切换（严重）

当前：

```python
_engine
_SessionLocal
_active_db_path
```

是：

# 全局共享状态

---

## 为什么危险

FastAPI 是并发服务。

现在：

两个用户同时切项目：

可能：

- A 请求读到 B 项目数据
- session 指向错误 db
- engine 热切换时竞争

这是：

# 线程安全问题

---

# 这是当前系统最大架构风险之一

目前只是因为：

- 本地单用户
- SQLite
- 开发模式

所以没炸。

但架构上已经危险。

---

# 正确方向

不要：

```python
switch_database()
```

全局切换。

---

## 正确方案

### 方案 A（推荐）

请求级：

```python
Depends(get_project_db)
```

每个请求绑定 db。

不要全局切换。

---

## 方案 B（后期）

真正工业级：

- PostgreSQL
- project_id 隔离
- 多租户

---

# 问题 2：:memory: 回切非常危险

当前：

```python
switch_database(":memory:")
```

非常危险。

因为：

你实际上：

# 正在切换真实 engine

---

## 后果

可能：

- metadata 丢失
- session 残留
- 内存库误引用

这属于：

# 隐式系统状态

后期极难排查。
